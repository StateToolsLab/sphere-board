# 自動配置の規則 — Sphere Board Starter v0.3.1

2026-10-05。実装は `app/layout.js`、表示範囲は `app/camera.js`、描画は `app/main.js`。この文書は、この配布物で実際に採用した表示規則を説明する。入力データの意味そのものを表示都合で定義し直さない。

## 1. 配置関数の境界

`SphereLayout.layout(map)` は Starter の map を受け取り、別の geometry オブジェクトを返す。map・nodes・edges・source へ書き込まず、座標を保存しない。乱数、時計、通信、フォント測定、画面幅、テーマを使わない。同じ入力を同じ実装で処理した結果は一致する。三角関数から得た座標は小数8桁に丸める。

座標の根拠は kind、明示された parent 関係、order、nodes の順、lanes、derived、group の planned、gateKind だけ。state、ready、currents、owner の中身、label、source は座標の根拠にしない。IDを番地やプロジェクト識別子として分解しない。依存・発生・回収・妨げは線として描くが、配置の階層を作る根拠にはしない。

## 2. 決定順

比較キーは `order → nodes[]の添字 → kind → id`。order は任意の整数で、0・負数も許す。同値なら配列順を保つ。指定と省略が混在する場合は、order指定の行を先に数値順に、省略した行を後に配列順に置く。省略したorderに配列の絶対添字を数値として補うことはしない。別工程への行挿入で添字がずれ、明示orderとの大小が逆転するのを防ぐためである。id と kind は最後の文字列比較であり、自然順ソートや番地解析ではない。

`order` を持つ行は数値順で先に並び、`order` がない行は `nodes[]` の順を保ちます。Starter を手書きする場合は、並びを安定させたい行に `order` を付けます。

## 3. フェーズと工程

phase が1個なら360度、複数なら `360度 / phase数` の等しい扇形を割り当てる。上から時計回りに、決定順で並べる。工程は親をたどって得られる phase に属する。phase がない入力にも、データへノードを足さない表示専用の1フェーズ枠を用意する。

各フェーズの工程は、まず非予定、次に `planned=true` を安定分割し、それぞれを決定順に並べる。「予定を外側へ」が工程間の order より優先する。工程の state が scheduled かどうかは配置に使わない。

工程番号を0始まりの k とすると、内容配置の内側基準は `120 + 460k`、外縁は `120 + 460(k+1)` 配置単位。最初の工程の背景領域だけは中心0まで塗り、次の工程は前工程の外縁から始まる。同じ半径を各フェーズで使う。工程の行数で帯幅や後続工程の半径を変更しない。予定領域は外側の帯のまま、境界を点線にする。

project / phase / group は選択できる構造アンカーと領域見出しであり、本線作業の珠として目立たせない。一覧・詳細にはこれらの行も省略せず載せる。

## 4. 工程内の本線・管制・ゲート

各扇形の端に小さな余白を置き、使用可能な角度の90%を lanes[] 順に等分する。残り10%は空・未登録レーン用の固定枠。未登録レーンが後から現れても、別工程の既存レーンの角度を変えないためである。lanes が空なら全角度を1枠として扱う。新たな lane の登録自体は構造変更に当たる。

本線 task は同じレーンの中で決定順に角度列へ置く。多い場合は工程内に半径方向の行も使い、角度列を先に進む順にする。列数・行数はその工程、そのレーンの行だけで決まる。工程間で再均等化しない。

management は内容配置の内側基準から85単位外の基準珠。本線の0.64倍で描く。同じ工程で密度調整が入っても、この相対寸法は変えない。集約点であって、次に取る本線作業として強調しない。ただし map に ready が明示されていれば ready の印そのものは隠さない。

gate は工程の外縁に固定。gateKind 未指定は explicit。explicit を先に並べ、その最初のものを主位置へ置く。残りは同じ外縁の近くへ交互に並べる。recheck / event は本線基準の0.65倍。明示ゲートが複数あれば、先頭を主位置とし、それ以外の明示ゲートは同じ基本寸法で残す。明示ゲートがないときは、再判定・イベントを勝手に explicit に変えない。

## 5. 派生、衛星、工程外

派生 task は親の位置から外向きの候補を、正面、左右の開きの順に試す。基本寸法は本線の0.72倍。親からの距離は珠・ラベル・駒席の予約寸法から決め、近い候補を優先する。issue / decision は0.68倍の衛星で、親の左右・外側・必要なら内側を候補にする。

親をたどっても工程に着かない行、project / phase を親とする衛星は、該当フェーズの最外工程のさらに外にある余白帯へ置く。特定工程に所属する関係を作らない。フェーズを親から決められない行は先頭フェーズの余白を表示上の置き場所とする。この代替位置も、所属を示す新しい edge にはしない。

ゲート自身を親とする派生など、親がすでに外縁にある境界ケースでは、外向きの枝を失わせないため、外縁直外36単位以内の小さな表示用余白も候補にする。これは特定工程への所属変更ではない。通常の工程内 task の派生にはこの例外を使わない。

回収済・未着手・進行中を含め、状態変化で派生の座標を作り直さない。派生を削除せず、状態形だけを描き替える。関係が実際に削除・変更された場合は構造変更なので別である。

## 6. 密度と駒の座席

全ての非構造珠で、owner が空でも同じ規則で座席を予約する。基準寸法では珠中心から `(50, -12)`、半径10。工程の密度係数と珠の相対寸法を掛けて、座席も一緒に縮める。`geometry.nodes[].seat` に中心と半径を返す。現在は見えない予約円で、駒の絵は描かない。担い手は既存のレーン色の帯と文字で示す。

珠、2行の短縮ラベル、座席を覆う予約円で、その工程だけの衝突を検査する。収まらなければ、その工程の表示寸法を `0.78^試行回数` に縮めて再配置する。別工程の帯幅・座標を押し広げない。これが、大きな入力でも工程間の局所性を維持するための選択である。

ラベルには明示的な予約矩形があり、SVG clipPath でその内側だけを描く。予約席や他の珠と重なるラベルは出さず、一覧・詳細へ残す。テーマのフォントが変わってもラベルが座席へはみ出さない。珠・座席の座標は変わらないが、別工程のラベル可視性まで不変にする契約ではない。

極端に密な工程では拡大か一覧が必要になる。帯を自動で拡張して別工程を動かす方式は、この版では採用しない。500ノードは既存の入力上限であって、全構造で同じ読みやすさを保証する数ではない。

## 7. 局所性の範囲

既存工程へ通常の行・派生・衛星を1行追加しても、他工程・他フェーズの珠の x/y は変えない。工程外の行の追加はその余白帯だけの再配置になる。

phase / group 自体の追加・削除、親関係・order・lanes の変更、工程の planned 切り替えは盤の構造変更であり、その影響範囲の再配置を許す。フェーズ数が変われば均等な扇形の角度も変わる。工程追加時まで既存全座標を固定するという保証ではない。

source 削除試験は、配置関数の独立性を調べる試験である。投影から source を削って編集可能な台帳へ変える手順ではない。投影の証跡・承認の省略を許す検証規則と、直接管理 map の規則は従来どおり別である。

## 8. 線

map.edges に存在する線だけを描く。parent は矢印のない薄い実線。ただし project / phase / group という構造見出しを端点に持つ parent は既定表示では隠し、端点の珠または見出しを選んだときだけ出す。工程・フェーズへの所属は同心帯・扇形の領域で読む。非構造の parent（派生・小課題・未確定事項など）は従来どおり既定表示する。dependency は Starter の `from → to`、すなわち前提から後続への矢印。origin は発生元から派生へ、return は派生から回収先への別曲線。同じ2点の場合は曲率の向きを分ける。blocks は破線と対象側の停止端。

曲線の調整と派生の開きは行うが、依存を使って工程やレーンを並べ替える処理、交差数の全体最小化探索は行わない。交差が残る場合は、選択ノードの関係だけを前面化して辿る。存在しない関係、戻り先、所属線は補わない。

## 9. auto / manual

layout.mode 未指定または auto は、x/y が入っていても自動配置。`layout.mode="manual"` かつ全ノードの x/y が有限数のときだけ、それらをそのまま使う。1行でも欠ければ全体を auto にし、確認事項へ理由を出す。一部だけ自動、一部だけ手動にはしない。

manual の指定位置が重なる場合は、座席衝突を警告する。指定位置を勝手に動かして解決しない。全ての手動配置で衝突を防げるという保証はしない。auto / manual の選択は投影の読み取り専用境界を変えない。

## 10. 初期表示、現在地、Ready、375px

配置関数には画面幅を渡さない。PCと375pxは同じ geometry を使う。

未判定ゲートは大きな4分節リング、ready=true は4方向の外付け把持印。状態の path を上書きしない。予定内の未判定ゲートもリングを消さない。既存の Starter の明示 currents も引き続き表示する。表示側で Ready を再計算しない。

初期カメラは `珠の寸法係数 × カメラ倍率 >= 0.70` を焦点ラベルの下限にする。現在地とReady全体がその下限を保ったまま入る場合だけ全体へ合わせる。入らない場合は、読めることを優先し、同時に読める組があれば最も近い現在地とReadyの組、なければ最も近い組の現在地を主焦点にする。近いReadyの名称は案内欄にも示し、表示範囲外ならその旨を出す。全ての現在地が入らなくても、総件数と `現在地 n/N`、そして「現在地へ」で順に巡回する。

「全体」は幅と高さの両方に合わせる。下限20%のような大きな縮小制限は設けない。現在地リングは画面上の半径12px以上、Readyは半幅10px以上を保つ。低倍率では珠本体が小さくても印を残す。近接ゲートの印同士が重なることはあり、件数と巡回・拡大を併用する。

ラベルは `珠の寸法係数 × カメラ倍率 >= 0.70` かつ予約矩形が空いているときだけ出す。初期表示と「現在地へ」は、この閾値をカメラ倍率の下限として直接使う。「全体」は全域を収めるため下限を持たず、ラベルを省いてよい。倍率0.24未満では、選択関係以外の非親子線を減らす。低倍率の小さな本文を無理に読ませない。工程順は盤上部の見出しにも残す。

一覧は全ノードと、親・前提・発生元・回収先・妨げを文字で出す。375pxで珠を選ぶと下からの詳細欄を開く。パン・ホイールズーム・ピンチズームはカメラだけを動かす。状態・実績・元データは編集しない。

## 11. 設計案 v0.1 §2 との違い

番地・address による整列を廃止し、今回確定した Starter の order と配列順へ置き換えた。複数フェーズは均等扇形、予定工程は安定分割で外へ置く。工程幅を固定して局所性を明確化し、密度増加を工程内の表示寸法で受ける。明示ゲートと再判定・イベントの主従、管制の相対寸法、駒の予約席、manual の成立条件も具体化した。

中心から外への工程順、親に近い派生・衛星、状態で場所を動かさないこと、線を推測で追加しないこと、同じ座標系を画面幅によらず使うことは維持している。正式な駒・状態形は今回決めていない。
